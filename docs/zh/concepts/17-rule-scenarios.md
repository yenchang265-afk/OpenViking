# 規則（Beta）

Rule 是 Agent 在特定條件下必須遵守的持久強約束，例如行動義務、禁止項和邊界。OpenViking 將規則材料批次編譯為可獨立理解的規則，再根據當前任務召回適用規則，供 Agent 在行動或回答前核驗。

當前 Beta 面向主動匯入和按需召回。普通會話提交不會自動觸發規則編譯，也沒有在每條使用者訊息或新會話開始時強制注入規則的內建流程。

## 與其他上下文型別的區別

| 型別 | 回答的問題 | 示例 |
| --- | --- | --- |
| Resource（資源） | 有哪些原始資料可查閱？ | 協議原文、程式碼倉庫、技術規範 |
| Memory（記憶） | 已知哪些事實、偏好和經驗？ | 使用者偏好簡潔回答、專案採用某個框架 |
| Skill（技能） | 如何完成這類任務？ | 倉庫審查步驟、報告生成方法 |
| Rule（規則） | 在什麼條件下必須做什麼或禁止做什麼？ | 宣告開源的倉庫必須提供可定位的許可證文本 |

Rule 的優先順序高於普通 Memory。它是一種獨立的上下文型別；雖然儲存在使用者的 `memories/rules/` 下，但使用專門的編譯和搜尋介面。把協議或規範作為 Resource 匯入，只儲存了資料，還需顯式編譯其中的強約束。

偏好、建議、事實、示例和單次任務不應提升為 Rule。編譯也不能把原文的“建議”改成“必須”，或弱化“必須”“禁止”。

## 適用場景

| 場景 | 規則來源 | Agent 如何使用 |
| --- | --- | --- |
| 法律協議核查 | 使用者提供的協議義務、禁止事項與例外 | 根據具體審查物件和已知事實召回約束，再核對文本或計劃動作 |
| 程式碼規範檢查 | 團隊開發規範、程式碼審查要求 | 根據當前倉庫、修改內容和執行階段召回規則，檢查擬提交的變更 |
| 開源許可證核查 | 使用者提供的許可證要求 | 讀取倉庫宣告和許可證檔案，核對觸發條件並記錄證據 |

例如，輸入“倉庫宣告自己是開源專案時，必須提供明確、完整且可定位的專案許可證文本”，可以形成：

| 欄位 | 示例 |
| --- | --- |
| `content` | 倉庫宣告自己是開源專案時，必須提供明確、完整且可定位的專案許可證文本。 |
| `applies_when` | 倉庫宣告自己是開源專案。 |
| `exception` | 空字串：原文沒有明確例外。 |
| Scenario | 專案許可證核查 |

主題相似不等於條件成立。Agent 必須依據可讀取的材料核驗條件；規則已經滿足時，它仍然適用。

## 規則如何組織

一條 Rule 儲存一個可獨立更新或撤銷的完整約束，包含 `content`、適用條件 `applies_when`、例外 `exception`、來源與原文證據，以及穩定標識 `atomic_id`、版本 `revision` 和狀態 `status`。空 `applies_when` 表示除例外外均適用。

Scenario 描述規則可能適用的實際情況，用於分組和召回，例如“專案許可證核查”。它不是來源文件的標題：同一份文件可以產生多個 Scenario，多份資料也可以複用同一 Scenario。

```text
viking://user/<user_id>/memories/rules/
└── repository-license/
    ├── abstract.md          # Scenario 描述
    └── project-license.md   # 完整 Rule 記錄
```

## 編譯流程

```text
規則文本、檔案、目錄或 URL
    → 讀取已有資源，或解析並匯入新來源
    → 召回已有 active / paused 規則
    → Compiler 提煉約束並生成變更計劃
    → 校驗結構、目標、原文證據和舊要求保留情況
    → 寫入 Rule / Scenario，非同步重新整理索引
```

Compiler 保留約束強度、條件、例外、閾值和單位，並拆分可獨立維護的規則。同一規則的演進更新原記錄，完整替代會建立新標識並歸檔舊記錄；已有規則完整覆蓋輸入時無需重複寫入。關鍵歧義或被拒絕的輸入會記錄原因，不寫入 Rule。

編譯介面先返回後臺任務。任務完成後檢查實際變更；規則寫入對應的索引任務可能仍在處理，使用前也要確認該任務完成。具體步驟見[規則校驗（Beta）](../workflows/02-rule-validation.md)。

## 搜尋與執行流程

```text
Agent 提交任務目標、物件、計劃動作和已知事實
    → 語義召回可能相關的 Scenario
    → Jev 過濾高置信度無關的 Scenario
    → 讀取其中的 active 規則，判斷適用條件與例外
    → 返回結構化規則和完整的約束文本
    → Agent 逐條核驗並約束行動或回答
```

搜尋預設返回適用分數達到 `0.65` 的規則，公開介面不設定固定 Top-K。非空適用條件下，例外分數達到閾值且嚴格高於適用條件分數時才否決；空適用條件下，例外達到閾值即否決。

Jev 未配置、不可用或返回無效結果時，受影響候選會放行。Rule 判斷失敗時返回 `judge="pass"`、`probability=1.0` 和 warning；這個分數表示放行，不是估算機率。Agent 仍需核驗條件和例外。

`rendered` 提供應用步驟和完整規則塊，可交給 Agent。搜尋判斷的是“規則是否適用”；是否滿足、違反或證據不足，由 Agent 對照任務事實判斷。空搜尋結果不能證明規則庫沒有相關約束；`delivery.complete` 也只表示命中規則完整交付，不保證全庫召回。

## 生命週期

| 狀態 | 編譯候選 | 搜尋候選 | 含義 |
| --- | --- | --- | --- |
| `active` | 是 | 是 | 啟用 |
| `paused` | 是 | 否 | 暫停，保留規則，不安排到期清理 |
| `archived` | 否 | 否 | 邏輯刪除，保留期結束後可被清理 |

使用者明確要求暫停或禁用時使用 `PAUSE`；恢復暫停規則使用 `RESTORE`。刪除、丟棄或移入回收站才使用 `ARCHIVE`。`UPDATE` 保留原有狀態。當前編譯介面不能恢復 archived 規則。

歸檔記錄儲存 `archived_at`，重複歸檔不重置時間。預設啟用定期清理，保留期為 30 天；實際物理清理發生在保留期結束後的掃描中，配置見[服務端 Rules 配置](../configuration/01-server.md#rules)。
