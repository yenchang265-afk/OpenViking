# 閘道器中的長對話

本頁寫給配置上下文配置和上游的管理員，也寫給長對話被截斷或被服務商以過長為由拒絕的使用者。讀完後你會知道閘道器何時、如何為長對話生成摘要，壓縮後模型收到什麼，以及要付出什麼代價。最先要檢查的是模型的[上下文視窗](#context-window)：沒有設定時，閘道器按 1,000,000 token 計算。

## 壓縮做什麼 {#long-conversations}

[壓縮](../guides/15-gateway.md#key-terms)讓對話始終不超出模型的上下文視窗（單次請求最多能容納的 token 數），預設開啟。對話接近視窗上限時，由同一個模型為目前為止的對話寫一份摘要，此後截斷點之前的全部內容都由這份摘要替代。客戶端裡顯示的歷史不受影響。開啟了儲存對話、模型也能用 OpenViking 的 `grep` 和 `read` 工具時，摘要末尾會附上[查詢被壓縮內容](#finding-what-was-cut)的方法。

在 Studio 中的位置：**上下文配置** → **長對話**。

| 設定 | 預設值 | 作用 |
| --- | --- | --- |
| **壓縮** | 開啟 | 對話接近上下文視窗時，用摘要替換較早的部分。 |
| **壓縮時機** | 視窗的 0.9 | 視窗用到多大比例時開始壓縮。 |
| **摘要長度上限** | 8,000 token | 模型寫一份摘要最多能用多少 token。 |
| **預設上下文視窗** | 未設定（按 1,000,000 token 計算） | 上游沒有列出的模型用這個視窗，見[設定模型的上下文視窗](#context-window)。 |
| **Agent 自管上下文視窗** | 關閉 | 實驗性功能，由模型自己開啟新視窗，見[下文](#experimental-agent-managed-context-windows)。 |

對話會一直沿用開始時的上下文配置，所以修改配置隻影響新對話，見[修改何時生效](06-manage-in-studio.md#when-changes-take-effect)。取值範圍和 API 欄位名見[配置參考](13-configuration.md#context-profile-settings)。

## 何時壓縮 {#when-it-compacts}

每收到一條新的使用者訊息或一個工具步驟（客戶端回傳自己工具執行結果的請求，即[請求型別](10-overview-and-requests.md#request-types)中的**工具步驟**），閘道器都估算一次視窗用量：取服務商為這段對話上一次回覆報告的 token 用量，加上之後新增訊息的估算值。估算值達到**壓縮時機**（預設是視窗的 0.9）時，閘道器先壓縮，再轉發請求。

例外情況：

- **服務商沒有報告用量。** 拿不到用量時（例如流式 Chat Completions 沒有設定 `stream_options.include_usage`），閘道器估算整個請求。
- **不觸發壓縮的請求。** 輔助請求、子 Agent 請求和 Token 計數請求不會觸發壓縮。
- **OpenViking 工具往返不檢查。** 閘道器只在請求到達時檢查視窗用量，所以它在一次請求內部代為執行的 OpenViking 工具往返不會被壓縮。工具輪數和 Token 預算預設都不限；要讓單次請求不超出視窗，請設定**每次請求的工具輪數**或 **Token 預算**（見[上限](04-openviking-tools.md#limits)）。

## 設定模型的上下文視窗 {#context-window}

閘道器要知道每個模型的上下文視窗有多大，才能及時壓縮。它按以下順序取第一個設定了的值：

1. 上游**上下文視窗**中該模型的條目，按發給上游的模型名（別名換算之後）匹配。
2. 上下文配置的**預設上下文視窗**。
3. 都沒有設定時，按 1,000,000 token 計算。

模型的視窗小於 1,000,000 token 時，請設定前兩項之一。否則閘道器壓縮得太晚，還沒等到壓縮，服務商就會以對話過長為由拒絕請求。如果你沒有許可權修改上游或上下文配置，請聯絡負責管理閘道器的人，見[誰能修改什麼](06-manage-in-studio.md#who-can-change-what)。

設定並確認模型的視窗：

1. 在 Studio 中開啟**上游**，編輯對應上游，在**模型** → **上下文視窗**中新增模型名及其視窗大小（單位為 token，至少 1,024）。上游設定儲存後立即生效。如果想讓這個上游沒列出的所有模型都用同一個視窗，改為在**上下文配置** → **長對話**中設定**預設上下文視窗**，這隻對新對話生效。
2. 發一條訊息，然後在**請求日誌**標籤頁展開這條請求。**上下文視窗**一行應顯示“約 … / *N* Token”，*N* 就是你填的視窗大小。

## 摘要怎麼生成 {#how-the-summary-is-written}

閘道器向同一個上游、同一個模型額外發一次非流式請求。客戶端的系統提示詞、工具和思考設定保持不變，所以大部分內容能命中服務商的[提示詞快取](01-how-it-works.md#replay)。純文本摘要做不到的設定會被去掉：強制的工具選擇改為不呼叫工具，結構化輸出格式和停止序列也不保留。

這次請求包含截斷點之前的對話，以及一條讓模型為自己寫摘要的指令。之前的摘要會併入新摘要。摘要要覆蓋：

- 使用者的目標和最新請求的原文；
- 關鍵決定和當前進度；
- 檔案、路徑和識別符號；
- 出過的錯誤和修正；
- 未完成的事項；
- 最近幾次工具結果裡的要點。

摘要是純文本，最長**摘要長度上限**（8,000）個 token。思考內容也計入輸出上限，而有些模型（如 DeepSeek V4.1）即使請求裡沒有思考設定也會預設思考，所以閘道器總在摘要長度上限之外再留 16,000 token 的輸出餘量；客戶端手動指定了思考預算時，改為加上這份預算。這次請求和其他請求一樣由服務商計費。

## 壓縮之後模型收到什麼 {#what-the-model-receives-afterwards}

截斷點的位置取決於請求型別：

| 請求 | 截斷點 | 模型收到的內容 |
| --- | --- | --- |
| 新的使用者訊息 | 緊挨在這條訊息之前 | system 和 developer 訊息、作為一條使用者訊息的摘要，以及這條新訊息 |
| 工具步驟 | 最近一次工具結果之後 | system 和 developer 訊息，以及摘要；模型從摘要出發繼續完成任務 |

摘要訊息開頭說明閘道器替換了對話較早的部分、這段內容不是使用者寫的；結尾附上這段對話開頭的閘道器說明和使用者畫像，所以壓縮後它們仍然保留。

之後凡是重發這段歷史的請求，包括輔助請求和 Token 計數請求，都做同樣的替換；子 Agent 通常傳送自己單獨的歷史，不受影響。每次壓縮讓服務商快取在截斷點失效一次，之後照常命中。

**截斷點之前的原文一概不保留**，最近幾輪也一樣。模型之前的回覆和其中的思考內容都依賴被替換掉的歷史，只保留一部分會破壞 Claude 的思考簽名。截斷點之後生成的內容照常傳送，包括思考內容。

### 查詢被壓縮的內容 {#finding-what-was-cut}

對話本身仍儲存在 OpenViking 裡。開啟了**儲存對話**、這段對話也提供了 `openviking_grep` 和 `openviking_read` 工具時，摘要末尾會附上查詢方法：

- 這段對話對應的 OpenViking 會話（`viking://user/<user_id>/sessions/<session_id>/`），以及會話中訊息的存放位置；
- 檢索步驟：先用具體的關鍵詞 grep 會話，拿到行號，再讀取匹配位置前後的內容。

截斷點落在一輪中間時，截斷點之前的部分會立即儲存到 OpenViking，模型在這一輪裡就能檢索到。

## 在請求日誌中檢視壓縮 {#see-compaction-in-the-request-log}

在**請求日誌**標籤頁展開一條請求（見[請求日誌](10-overview-and-requests.md#requests)），**上下文視窗**一行會顯示：

| 顯示內容 | 含義 |
| --- | --- |
| 約 *X* / *Y* Token（*P*） | 估算的視窗用量，以及閘道器採用的視窗大小 *Y* |
| 傳送時較早的歷史已被替換 | 這次請求用摘要替代了截斷點之前的歷史 |
| 生成了約 *N* Token 的摘要，用時 *T* | 這次請求觸發了壓縮，寫摘要用了 *T* |
| 壓縮失敗（*原因*），已傳送完整歷史 | 見[壓縮失敗時](#when-compaction-fails) |
| 摘要已保留，但用量仍達到壓縮時機（`still_over_threshold`） | 摘要已寫好並用上，但對話仍佔滿視窗，見[壓縮失敗時](#when-compaction-fails) |

## 壓縮失敗時 {#when-compaction-fails}

摘要請求失敗，或者回復裡呼叫了工具、內容為空、因長度上限被截斷時，閘道器改為傳送完整歷史。請求詳情會顯示**壓縮失敗**及原因，並且 60 秒內不再為這段對話嘗試壓縮。

只有一種情況會保留摘要：摘要寫完後用量仍達到**壓縮時機**（例如系統提示詞和工具本身就佔了視窗的大部分）。這時閘道器照常使用這份摘要，同時記一次失敗，同樣等 60 秒再嘗試。

各個原因的含義和處理方法見[長對話超出上下文長度](12-troubleshooting.md#long-conversations-hit-the-context-limit)。

## 副作用 {#side-effects}

**不再生成 Working Memory 摘要。** 摘要由對話所用的模型生成，不使用 OpenViking 的會話摘要。閘道器新建的 OpenViking 會話都關閉了 Working Memory：提交時照常歸檔訊息、提取記憶，只是不生成會話摘要。

**記憶預算重新計算。** 每壓縮一次，**單個上下文視窗預算**（見[召回記憶](08-context-profiles.md#recall-memory)）就重新計算，截斷點之前補充過的記憶可能再次補充。

**客戶端仍傳送完整歷史。** 閘道器壓縮後，客戶端還是傳送完整歷史，閘道器在每個請求裡替換截斷點之前的部分。客戶端看到的用量很小，所以按用量決定何時壓縮的客戶端很少再自己壓縮。

**特別長的會話可能超出請求大小上限。** 客戶端的歷史越來越長，特別長的會話最終可能超出請求大小上限：請求體超過 32 MiB 會被拒絕，返回 HTTP 413（見[客戶端收到閘道器返回的錯誤](12-troubleshooting.md#clients-get-an-error-from-the-gateway)）。運維人員可以用 `max_body_bytes` 調整這個上限（見[閘道器欄位](13-configuration.md#gateway-fields)）；閘道器前面的反向代理允許的請求體也不能比它小（見[反向代理和 HTTPS](../guides/22-gateway-operations.md#reverse-proxy-and-https)）。

**客戶端自己壓縮會換到新會話。** 客戶端壓縮或編輯歷史後，閘道器把新歷史儲存到新的 OpenViking 會話。檢索工具可用時，新歷史開頭的閘道器說明會告訴模型之前的會話在哪裡。

## 實驗性：Agent 自管上下文視窗 {#experimental-agent-managed-context-windows}

開啟 **Agent 自管上下文視窗**（預設關閉）後，由模型自己決定何時開啟新的上下文視窗，並自己寫交接筆記，不必等閘道器生成摘要。閘道器會給模型兩個工具，並在視窗快滿時提醒它。這項設定只對能使用 [OpenViking 工具](04-openviking-tools.md#agentic-memory-for-any-client)的對話生效，其他對話照常[壓縮](#long-conversations)；開啟壓縮時，如果模型一直不開新視窗，壓縮仍會兜底。

在 Studio 中的位置：**上下文配置** → **長對話** → **Agent 自管上下文視窗**（標有**實驗性**），以及**軟提醒時機**（0.7）和**硬提醒時機**（0.85）。效果取決於所用的模型，後續版本中的行為也可能調整。

### 模型多了什麼 {#what-the-model-gets}

兩個額外的工具。它們不在上下文配置的**工具**清單裡，只由這項設定控制。

| 工具 | 作用 |
| --- | --- |
| `openviking_new_context(reason, notes, next_steps)` | 開啟新視窗，`next_steps` 可省略。 |
| `openviking_context_remaining()` | 返回視窗序號、已用和剩餘 token 的估算值、本視窗內的使用者輪數、距使用者上一條訊息的時間，以及一句建議。 |

`openviking_new_context` 必須在一輪裡單獨呼叫；和其他工具同一輪呼叫時，這一輪的每個呼叫都返回錯誤，視窗不重置。閘道器在本次請求裡已經在同一位置替換過上下文（例如剛壓縮過）時，它同樣返回錯誤。

模型還會看到：

- **開頭的閘道器說明裡多一行**，告訴模型它用這兩個工具自己管理上下文視窗。
- **一行狀態**：每條新的使用者訊息之後，記憶塊末尾附上 `[context-status] window wN · ~X/Y tokens (P%) · T since your previous message`。
- **軟提醒**：視窗用到**軟提醒時機**（0.7）時，閘道器提醒一次，要求模型做完當前這一步就開啟新視窗，並在交接筆記裡記下之後要用的確切路徑、行號和取值。
- **硬提醒**：用到**硬提醒時機**（0.85）時，要求模型立即開啟新視窗，此後每一步都重複，直到模型開啟新視窗或壓縮接手。

提醒附在新的使用者訊息上，工具步驟裡則附在客戶端回傳的工具結果上；閘道器自己執行的 OpenViking 工具往返之間不加提醒。

### 模型開啟新視窗時 {#when-the-model-starts-a-new-window}

模型呼叫 `openviking_new_context` 後，閘道器把目前為止的對話換成一個視窗頭，模型在同一條回覆裡接著工作。視窗頭依次包含：

1. 這是模型開啟的第 N 個視窗，內容不是使用者寫的；
2. reason、notes 和 next_steps；
3. 使用者最新一條訊息的原文；
4. 檢索之前視窗的方法（條件和[壓縮](#finding-what-was-cut)時相同）；
5. 這段對話開頭的閘道器說明。

之後的請求會根據客戶端的歷史重建同一個視窗。重置之前的內容會立即儲存到 OpenViking，之後仍可檢索；reason 和 notes 只出現在視窗頭裡，不儲存到 OpenViking。每次重置讓服務商快取失效一次，但不需要摘要請求。

在請求日誌中，每條請求的**上下文視窗**一行會顯示視窗序號（“第 *N* 個視窗，由模型管理”），模型開啟了新視窗時顯示“模型開啟了新視窗”，還會顯示模型收到了哪種提醒（“已提醒模型儘快開啟新視窗”或“已要求模型立即開啟新視窗”）。
