# 在 Studio 中管理 OpenViking 閘道器

本頁面向在 Studio 裡使用閘道器頁面的人，說明各標籤頁的用途、誰能修改什麼，以及儲存的修改何時生效。用你的 OpenViking API 金鑰開啟 Studio（[本地 dev 模式](02-quickstart.md#local-server-no-api-key)的服務無需金鑰），在側邊欄選擇 **OpenViking 閘道器**；獨立部署的閘道器在自己的 `/studio/` 下提供 Studio。上游和上下文配置由同一 OpenViking 帳號下的所有使用者共享，閘道器金鑰和請求日誌則屬於各個使用者。

## Studio 標籤頁 {#studio-tabs}

閘道器頁面共有六個標籤頁，每行都連結到詳細說明該標籤頁的文件。

| 標籤頁 | 用途 | 資料歸屬 | 詳見 |
| --- | --- | --- | --- |
| **概覽** | 一眼看清執行狀況：請求數、快取命中率、召回的記憶、OpenViking 狀態和降級請求。第一個請求到達之前，這裡顯示**快速開始**清單。 | 自己的請求；帳號管理員和 root 看到整個帳號的 | [概覽](10-overview-and-requests.md#overview)、[快速開始清單](#get-started-checklist) |
| **上游** | 新增、編輯、測試和匯入閘道器轉發請求的模型端點。 | 帳號內共享 | [上游](07-upstreams.md#upstreams) |
| **上下文配置** | 新建和編輯上下文配置：召回、儲存、長對話和 OpenViking 工具。 | 帳號內共享 | [上下文配置](08-context-profiles.md#context-profiles) |
| **金鑰** | 簽發和吊銷閘道器金鑰；帳號管理員和 root 還能刪除某個使用者的閘道器資料。 | 自己的金鑰；帳號管理員和 root 管理整個帳號的 | [閘道器金鑰](09-gateway-keys.md#gateway-keys) |
| **請求日誌** | 每個模型請求的記錄，包括補充的記憶、Token 用量、問題和儲存狀態。 | 自己的請求；帳號管理員和 root 看到整個帳號的 | [請求日誌](10-overview-and-requests.md#requests) |
| **接入** | 閘道器地址，以及各客戶端可直接複製的配置。 | 所有人相同 | [接入客戶端](03-connect-clients.md#connect-clients) |

## 誰能修改什麼 {#who-can-change-what}

能否修改[上游和上下文配置](../guides/15-gateway.md#key-terms)，取決於一項部署設定：[閘道器管理金鑰](../guides/22-gateway-operations.md#gateway-management-key)。預設不設定，是否設定由部署閘道器的人決定。

| Studio 中的操作 | 沒有設定管理金鑰 | 設定了管理金鑰 |
| --- | --- | --- |
| 檢視上游和上下文配置，並在簽發金鑰時選用 | 本帳號所有登入使用者 | 所有登入使用者；只讀檢視看不到上游的 API Key 和請求頭 |
| 新增、修改或刪除上游和上下文配置 | 本帳號所有登入使用者 | 必須先[解鎖編輯](#unlock-editing)，帳號管理員和 root 也不例外 |
| 測試上游（連線測試或模型測試） | 本帳號所有登入使用者 | 必須先解鎖；只讀時不顯示**測試**按鈕 |
| 匯入 OpenViking 模型配置（僅限嵌入式部署） | 只有 root，包括本地 dev 模式 | 必須先解鎖 |
| 簽發閘道器金鑰 | 使用者給自己簽發；帳號管理員可給本帳號的使用者簽發；root 先在側邊欄切換帳號 | 同左，管理金鑰不額外授予任何許可權 |

測試之所以需要寫許可權，是因為測試會使用已存的憑證，模型測試還會被服務商計費。簽發金鑰的細節見[閘道器金鑰](09-gateway-keys.md#gateway-keys)；包括管理 API 在內的完整規則見[許可權矩陣](../api/25-gateway.md#credentials-and-account-scope)。

如果還沒有可用的上游或上下文配置、自己又無權修改，**快速開始**清單會顯示正在等待閘道器管理員新增。這時請聯絡部署閘道器的人。

## 解鎖編輯 {#unlock-editing}

設定了[閘道器管理金鑰](../guides/22-gateway-operations.md#gateway-management-key)後，“上游”和“上下文配置”標籤頁預設只讀，需要在當前瀏覽器標籤頁裡解鎖。帳號管理員或 root 的 API 金鑰不能解鎖，閘道器金鑰（`ovgw_…`）也不行。

1. 在“上游”或“上下文配置”標籤頁的只讀提示中，點**輸入閘道器管理金鑰**。
2. 貼上管理金鑰，點**解鎖**。`openviking-server init`、`openviking-gateway init` 和 Studio 的**開啟閘道器**生成的金鑰都以 `ovgm_` 開頭；對話方塊裡的**在哪裡找？**列出了它的存放位置。
3. 頁面提示“已解鎖，現在可以修改上游和上下文配置”，頁頭顯示“可修改上游和上下文配置”和**鎖定**按鈕。

解鎖只對當前瀏覽器標籤頁有效，直到你點**鎖定**或關閉這個標籤頁。服務端更換管理金鑰後，Studio 會自動鎖定，並提示“閘道器管理金鑰已失效，上游和上下文配置恢復為只讀。”如果沒人知道金鑰，見[忘記閘道器管理金鑰](../guides/22-gateway-operations.md#lost-the-management-key)。

## 快速開始清單和快速模式 {#get-started-checklist}

第一個請求到達之前，“概覽”標籤頁上會顯示**快速開始**清單，按順序列出四步：**新增上游**、**建立上下文配置**、**簽發閘道器金鑰**、**接入客戶端**。客戶端發出第一個請求後，清單自動隱藏。

還沒有任何[閘道器金鑰](../guides/15-gateway.md#key-terms)時，清單裡還有一張**快速模式**卡片，點**一鍵生成金鑰**即可完成前三步：

| 步驟 | 快速模式做什麼 |
| --- | --- |
| 上游 | 沿用已有的可用上游；一個都沒有時，把 OpenViking 自身的模型配置（`ov.conf` 裡的 VLM）[匯入](07-upstreams.md#import-openviking-model-settings)為上游。 |
| 上下文配置 | 沿用已有的上下文配置；一個都沒有時，用推薦設定新建一份，名為“預設”。 |
| 金鑰 | 為當前使用者簽發一個名為“快速模式”的金鑰，繫結所有可用上游。本地 dev 模式以外，root 改為在簽發對話方塊裡選擇金鑰歸屬的使用者。 |

同時滿足以下條件的上游才算可用：

- 已啟用；
- API Key 由閘道器保管（沒有設為**每個客戶端自帶 API Key**），並且已經儲存了金鑰；
- 至少列出一個模型或別名（**模型**列表為空的上游不算，所以即使已經有這樣的上游，快速模式也會匯入模型配置）；
- 不是仍被[攔截](07-upstreams.md#blocked-upstreams)的 [Coding Plan 上游](07-upstreams.md#coding-plan-keys)。

例外情況：

- 匯入後仍沒有閘道器能直接轉發的模型時，卡片會說明原因，這時請在第 1 步（**新增上游**）手動新增上游。
- 設定了管理金鑰、而快速模式需要新建上下文配置或匯入模型時，卡片會先要求你用管理金鑰解鎖。
- 只有部分使用者能匯入模型配置：未設定管理金鑰時是 root（本地 dev 模式下任何人都可以），設定了管理金鑰時是用它解鎖的人；獨立部署的閘道器則完全無法匯入。不能匯入時，只有已經存在可用上游才會顯示這張卡片。

## 修改何時生效 {#when-changes-take-effect}

上游或上下文配置儲存後，會作用於所有使用它的閘道器金鑰，不需要重新簽發金鑰。區別只在於已經開始的[對話](../guides/15-gateway.md#key-terms)能不能用上修改：

| 修改內容 | 何時生效 |
| --- | --- |
| 除優先順序外的任何上游設定，例如 API Key、模型、**啟用** | 立即生效，進行中的對話也一樣。停用上游會對它的對話產生什麼影響，見[路由](07-upstreams.md#routing)。 |
| 上游優先順序 | 只對之後開始的對話生效。進行中的對話只要原來的上游還能服務，就一直留在那裡。 |
| 任何上下文配置 | 只對之後開始的對話生效。 |
| 閘道器金鑰 | 金鑰不能編輯。要更換金鑰的上下文配置、上游、允許的模型或歸屬使用者，請簽發新金鑰並吊銷舊金鑰，見[簽發之後](09-gateway-keys.md#after-issuing)。 |

對話在第一個請求時記下當時的上下文配置並一直沿用，因為中途改變模型看到的內容會破壞服務商的[提示詞快取](01-how-it-works.md#replay)。所以客戶端多快能用上新的上下文配置，取決於它多久開始一次新對話：

- 每次聊天都新開對話的客戶端，很快就能用上新設定。
- Claude Code、Codex 以及傳送固定會話請求頭的客戶端，會把一段對話延續很多天。它們一直沿用舊設定，直到開始新對話，或者這段對話閒置滿 30 天（`session_ttl_days`），此時閘道器會刪除這段對話的狀態。

閘道器如何區分不同的對話，見[閘道器如何識別對話](03-connect-clients.md#how-conversations-are-recognized)。
