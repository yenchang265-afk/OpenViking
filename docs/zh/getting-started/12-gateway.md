# 閘道器接入

OpenViking 閘道器連線客戶端與模型服務，在轉發請求時補充相關記憶，並將對話儲存到 OpenViking，供後續提取和複用。對於支援自定義 Base URL 和 API Key 的相容客戶端，可以通過修改連線配置接入記憶能力。

本節使用一個 Python 樣例完成 **連線閘道器 → 傳送對話 → 檢視記憶 → 在新會話中使用**：先告訴模型虛構“山嵐專案”的評審約定，再開啟另一段對話，檢視回答是否沿用這些約定。

::: info Beta
OpenViking 閘道器目前處於 Beta 階段，後續可能調整介面和配置方式。升級時，請結合更新說明核對現有接入配置。
:::

## 準備環境

本節採用本機服務，開始前請準備：

- **OpenViking 服務**：按[快速開始](02-quickstart.md#本地服務)完成安裝和模型配置，確保 Embedding 和 VLM 可用。閘道器包含在 OpenViking 中，啟用後與資料服務共用埠。
- **Python 3**：用於執行樣例，安裝方法見[準備本地執行環境](02-quickstart.md#準備本地執行環境)。樣例只使用 Python 標準庫。
- **CLI 連線**：按 [CLI 入門](05-cli-setup.md)連線本機服務，供後續檢視會話和記憶。CLI 與閘道器金鑰應對應同一 OpenViking 使用者；預設本機模式使用 `default` 使用者。
- **上游模型**：準備支援 **OpenAI Chat Completions** 協議的模型服務地址、模型名和 API Key，供本節樣例傳送請求。

以下操作會呼叫上游模型，並把虛構專案約定寫入當前使用者的記憶；記憶提取也會呼叫服務端配置的模型，按所選服務計費。遠端服務的身份與許可權配置見[閘道器快速上手](../gateway/02-quickstart.md#remote-server-api-keys)。

## 開啟本機閘道器

執行初始化嚮導，在已有配置的選單中選擇 **Update gateway**，啟用閘道器：

```bash
openviking-server init
```

儲存配置後，在原服務終端停止服務，再使用原來的啟動命令啟動。例如：

```bash
openviking-server
```

如果原服務還啟用了 VikingBot，啟動時保留 `--with-bot` 等已有引數。

開啟 [Studio](http://127.0.0.1:1933/studio/)，在側邊欄選擇 **OpenViking 閘道器**。本機閘道器地址為 `http://127.0.0.1:1933/gateway`，後續樣例會使用這個地址。

以 Studio 顯示的閘道器地址為準。下方截圖使用本機埠 `1934`；如果你的服務也使用其他埠，請同步替換後續命令中的地址。點選截圖可檢視原圖。

## 配置模型與記憶

在 Studio 中依次準備上游、上下文配置和閘道器金鑰：

### 配置上游

上游是閘道器轉發請求時使用的模型服務。在“上游”標籤頁，選擇或新增支援 **Chat Completions** 的上游，填寫模型服務地址和憑據，並通過頁面的測試功能確認連線或模型可用。

閘道器可能已從服務端 VLM 配置匯入上游。可以直接檢查並使用匹配的配置；匯入的 Coding Plan 上游按頁面提示完成確認。閘道器按請求協議轉發，本節樣例使用 Chat Completions，所選上游也需要支援該協議。

在上游編輯頁選擇 **Chat Completions**，根據模型服務提供的資訊填寫 **Base URL**，並核對下方顯示的完整請求地址。

[![Studio 上游編輯頁：選擇 Chat Completions 並核對 Base URL](/quickstart/gateway/upstream-zh.jpg)](/quickstart/gateway/upstream-zh.jpg)

### 設定上下文

上下文配置決定如何召回記憶和儲存對話。在“上下文配置”標籤頁新建一份配置，例如命名為“山嵐專案體驗”，使用以下設定：

| 設定 | 本節取值 | 作用 |
| --- | --- | --- |
| 召回記憶 | 開啟 | 為新訊息補充相關記憶 |
| 檢索範圍 | 記憶 | 使用已儲存的專案約定 |
| 儲存對話 | 開啟 | 將對話寫入 OpenViking，供後續提取記憶 |
| 最新回覆等待時長 | 30 秒 | 對話空閒後儲存最後一輪並提交會話 |
| 保留最近訊息 | 0 | 讓這段短對話的訊息參與本次歸檔與記憶提取 |
| 顯示召回摘要 | 開啟 | 在回覆中檢視補充記憶的摘要 |
| OpenViking 工具 | 關閉 | 通過自動召回和儲存完成本次流程 |

在配置編輯頁選擇“召回記憶”，開啟“顯示召回摘要”，並在“檢索範圍”中勾選“記憶”。

[![Studio 召回記憶設定：開啟召回摘要，檢索範圍選擇記憶](/quickstart/gateway/recall-zh.jpg)](/quickstart/gateway/recall-zh.jpg)

接著選擇“儲存對話”，將“最新回覆等待時長”設為 **30 秒**，“保留最近訊息”設為 **0**。完成後，在“OpenViking 工具”分組關閉工具並儲存配置。

[![Studio 儲存對話設定：等待時長為 30 秒，保留最近訊息為 0](/quickstart/gateway/capture-zh.jpg)](/quickstart/gateway/capture-zh.jpg)

儲存配置後，用它簽發下面的金鑰並開始新對話。配置修改對之後開始的對話生效；日常使用時，可以按任務需要調整等待時間和訊息保留策略，詳見[上下文配置](../gateway/08-context-profiles.md)。

### 簽發金鑰

在“金鑰”標籤頁簽發一把用於本次體驗的閘道器金鑰，選擇剛才的上下文配置和上游。複製彈窗顯示的完整 `ovgw_…` 值，供樣例連線使用；完整金鑰僅在簽發時顯示一次。

在簽發表單中填寫名稱，核對“給誰用”，並選擇已準備的上下文配置與上游。如果上游顯示“已攔截”，先返回上游頁按提示核對憑據和套餐適用條件，確認可用後再傳送請求。

[![Studio 簽發閘道器金鑰表單：填寫名稱，選擇上下文配置和上游](/quickstart/gateway/key-zh.jpg)](/quickstart/gateway/key-zh.jpg)

客戶端使用這把閘道器金鑰訪問模型，模型服務商的 API Key 儲存在上游配置中。檢視會話和記憶的 `ov` CLI 繼續使用原有的 OpenViking 連線配置。

## 傳送兩輪對話

下載 [Python 樣例](/quickstart/gateway-demo-v1.zip)，在終端中進入下載目錄並解壓：

```bash
unzip gateway-demo-v1.zip
```

解壓後得到 `gateway-demo.py`。下面的命令適用於 macOS / Linux 終端，先設定閘道器地址和模型名。將 `<上游模型 ID>` 替換為剛才上游中可用的模型名：

```bash
export GATEWAY_URL=http://127.0.0.1:1933/gateway
export GATEWAY_MODEL='<上游模型 ID>'
```

執行下面的命令後輸入閘道器金鑰並回車，輸入過程不會顯示金鑰字元：

```bash
read -r -s GATEWAY_KEY
export GATEWAY_KEY
```

傳送兩輪對話，向模型提供山嵐專案的約定：評審固定檢查四項風險、報告使用 Markdown、檔名為 `mist-review.md`。

```bash
python3 gateway-demo.py capture --language zh --run v1
```

樣例先傳送約定，再攜帶完整的第一輪訊息傳送“謝謝”。終端應依次顯示兩次回覆。第二次請求中的歷史用於儲存第一輪；最後一輪會在對話空閒達到配置的等待時長後儲存並提交。

在 Studio 的“請求日誌”中確認兩次請求成功，再到“會話”頁面找到包含山嵐專案約定的 `gateway-…` 會話。以服務實際生成的會話 ID 為準，後續 CLI 檢查使用這個 ID。

<a id="等待記憶並開啟新會話"></a>

## 檢視生成的記憶

停止傳送訊息後，閘道器會按配置等待 30 秒再提交最後一輪，後臺記憶提取還需要額外時間。可以每隔 10 秒檢視一次，先等待最多 5 分鐘。仍在處理時保留會話和任務 ID，稍後繼續檢查；出現失敗或取消狀態時，檢視對應錯誤或原因。

先列出會話，並將 `<gateway-session-id>` 替換為 Studio 中找到的會話 ID，檢視提交情況：

```bash
ov session list
ov session get <gateway-session-id>
```

再檢視記憶提取任務。找到 `resource_id` 與該會話 ID 對應的任務，將其 `task_id` 填入下一條命令：

```bash
ov task list --task-type session_commit
ov task status <task_id>
```

任務狀態為 `completed` 後，從任務結果中複製 `archive_uri`，檢視記憶變更：

```bash
ov read "<archive_uri>/memory_diff.json"
```

從 `operations.adds` 或 `operations.updates` 中複製記憶的 `uri`，讀取正文：

```bash
ov read "<記憶 URI>"
```

確認正文包含四項風險、Markdown 格式和 `mist-review.md` 三項約定後，再開啟新會話。記憶的名稱和分類以實際生成結果為準。

## 在新會話中使用

在同一終端中執行召回階段，沿用閘道器地址、金鑰和模型設定：

```bash
python3 gateway-demo.py recall --language zh --run v1
```

這條命令啟動新的 Python 程序，並使用不同的會話標識。它只傳送“按已儲存的山嵐專案約定準備評審清單，並給出交付檔名”的任務，具體約定由閘道器從記憶中補充。

檢視回復是否包含四項風險的檢查位置、使用 Markdown，並給出檔名 `mist-review.md`。樣例沒有提供具體風險內容，回答可以列為待補充，或明確標註為建議。

## 檢查結果

結合記憶正文、回覆中的召回摘要和 Studio 請求日誌，分別核對以下結果：

| 環節 | 預期結果 |
| --- | --- |
| 請求 | 兩次模型請求成功，終端收到回覆 |
| 儲存 | 對應會話及其歸檔中包含專案約定 |
| 提取 | 任務完成，記憶正文保留三項約定 |
| 召回與使用 | 新會話有召回記錄，回答遵循約定 |

回覆措辭可以不同。核對時既要看記憶是否被召回，也要看回答是否使用了其中的資訊。

## 常見問題

| 現象 | 處理方法 |
| --- | --- |
| 請求失敗或模型不可用 | 檢查閘道器地址、金鑰繫結的上游、模型名和 Chat Completions 協議，並檢視請求日誌 |
| Studio 中找不到會話 | 檢查儲存對話開關，確認當前使用者與閘道器金鑰繫結使用者一致，並檢視請求的儲存狀態 |
| 有會話但沒有生成記憶 | 檢查空閒等待時間、保留最近訊息數和 `session_commit` 任務狀態 |
| 已生成記憶但沒有召回 | 核對金鑰繫結的使用者、上下文配置和檢索範圍；修改配置後用新會話重試 |
| 有召回記錄但回答遺漏約定 | 對照記憶正文和回覆，請模型根據已儲存約定修訂 |

更多問題見[閘道器排障](../gateway/12-troubleshooting.md)。

## 繼續使用

完成後，可以按[客戶端接入](../gateway/03-connect-clients.md)將自己的應用連線到閘道器。遠端服務和團隊配置見[閘道器快速上手](../gateway/02-quickstart.md)。

再次體驗時，為兩條樣例命令使用相同的新 `--run` 值，以建立新的一組會話。相同使用者的已有記憶仍可被召回；如需從空白記憶開始，可使用單獨的演示使用者。

體驗結束後，可在 Studio 中撤銷本次閘道器金鑰，並根據會話和 `memory_diff.json` 按需清理演示資料。若本次更新了已有記憶，先核對修改內容，保留仍需使用的資訊。
