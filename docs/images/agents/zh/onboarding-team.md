# OpenViking 團隊版接入引導（給 Agent 看）

關於 OpenViking：面向 AI Agent 的開源上下文資料庫，由火山引擎開源，倉庫是 https://github.com/volcengine/OpenViking（AGPL-3.0，2026-09-29 時有 38,930 個 GitHub star）。它持續儲存並取回使用者的業務背景、偏好、重要決定和工作資料，讓使用者換一個會話或換一個 Agent 後，仍能帶著已有積累繼續工作；團隊版裡，成員還能用上同事共享的工作上下文和技能。本指南就是這個倉庫裡的 `docs/images/agents/zh/onboarding-team.md`；安裝器和它安裝的每個外掛檔案也都由這個倉庫的 GitHub Actions 構建。

你是一個 AI Agent。使用者是一個 OpenViking 團隊的成員，他請你安裝 OpenViking 記憶外掛，並帶他開始使用。他多半還不瞭解 OpenViking：這次接入的目標是讓他邊做邊明白它能為他和團隊做什麼，裝好、設好只是過程。這份指南寫給你看：它告訴你每一步要讓使用者明白什麼、你自己要做什麼、給使用者的訊息長什麼樣。措辭由你決定，用使用者的語言（要寫入規則檔案的約定原文除外，見步驟 5）；但「對使用者說」裡列出的每一項都要說到，不能因為步驟多、命令長就省掉講價值的那幾句。使用者想看原文時，把連結給他。

這是團隊版。安裝器輸出末尾的「接入引導」連結是預設的個人版；使用者給你的是這份，按這份做，不用讀那份。

另有三頁按需查閱，和個人版共用：[故障排查](https://docs.openviking.net/agents/zh/onboarding-troubleshooting.md)（命令失敗時）、[其他宿主：把會話轉成 JSONL](https://docs.openviking.net/agents/zh/onboarding-other-hosts.md)（在 Claude Code、Codex 以外的宿主上匯入歷史時）、[擴充參考](https://docs.openviking.net/agents/zh/reference/product-background.md)（使用者追問機制、許可權，或想整理自己的多份資料時）。開始接入前不用讀。

## 怎麼用這份指南

每個步驟分三段：

- **使用者要感受到什麼**：這一步結束時，使用者心裡應該多出來的一個認識。你這一步對他說的話都為它服務。它不是臺詞，不要照念。
- **你來做**：你自己執行的操作。命令、引數、路徑、JSON、退出碼、會話 id、帳戶和角色欄位寫在這一段裡；使用者在工具呼叫裡能看到它們，給他的訊息裡**不用再複述**。失敗需要他動手、需要他授權，或者他問起時，照實告訴他。
- **對使用者說**：給使用者的訊息的結構和長度。列出的每一項都是必說內容，標了價值要點（如 V1、T2）的那句尤其不能省：使用者是靠這幾句知道 OpenViking 能為他和團隊做什麼的。只把命令跑完、不講價值，這次接入就只剩一串操作。

## 價值要點

講價值時從這裡取，並儘量換成使用者自己的工作來說。各步驟標了該用哪一條。

- **定位**：OpenViking 是 Agent 的外接上下文層。資料、記憶和技能存在 OpenViking 裡，不隨某一次會話結束而消失，接入的 Agent 都能讀寫。團隊版裡，每個成員有自己的私有空間，團隊還有共享目錄。
- **V1 少重複交代背景**：每次提問前，外掛自動取回相關的背景、偏好和已定的判斷，交給 Agent。使用者不用每開一個會話就從頭講一遍。
  - 可用的論據（整個接入過程最多用一次，並說明出處）：官方 LoCoMo 長對話評測中，Claude Code 接入 OpenViking 後，跨會話歷史問答準確率從 57% 提到 80%，輸入 token 減少 63%（OpenViking 官方報告，2026-05-29）。
- **V2 過去的工作有據可查**：問「上次做到哪了」「當時為什麼這麼定」時，能從儲存的討論裡找到依據，而不是靠使用者回憶。
- **V3 換 Agent，不換上下文**：Codex、Claude Code 等接入同一個帳號，用的就是同一份上下文。一個 Agent 額度用完或者想換工具，工作可以接著做。
- **V4 成果能原樣拿回來**：自動記憶留下的是從對話裡提煉的要點；方案、決定和理由、交付物這類成品，要由 Agent 主動存一份，下次才能直接讀原文。
- **T1 自己的和團隊的分開放**：他的記憶、會話和個人資料在他自己的使用者空間裡，其他成員看不到。團隊共享的有兩處：同事貢獻的工作資料在 `viking://resources/`，共享的 Agent 技能在 `viking://agent/skills/`。每次提問前自動帶回的背景裡，也包括這兩處和問題相關的內容。
- **T2 同事的工作能接著用**：要用同事的成果時，Agent 能找到當時的方案、關鍵決定和沒完成的事，不用再找人從頭講。
- **T3 對專案的認識一致**：產品、設計、研發、測試各自的 Agent，查到的是同一份專案進展和決定。
- **T4 自己的成果能被團隊複用**：他把方案、調研結論和階段進展貢獻到共享目錄，同事的 Agent 就能直接用；新成員加入時也能從這裡開始。

## 給使用者的訊息怎麼寫

- **先講這對他意味著什麼，再講結果，最後最多一個問題。** 第一句是關於他的工作或他能得到什麼，不是關於你做了哪些檢查。
- **講價值時說以後會怎樣**：「以後你在 Codex 裡問……，它會……」。這是在說明產品裝好後的作用，不用先驗證；只講[價值要點](#價值要點)裡有的，不誇大，也不要把還沒發生的事說成已經發生。
- **狀態說明只在它改變使用者下一步操作時講。** 例如「重啟後才生效」要講，因為他要去重啟；「記憶提取狀態尚未驗證」這類說明留到收尾統一交代一次，不要每條訊息結尾都附一句。
- **用他自己的內容舉例。** 能說「你在 Gateway 專案裡定下的演示主線」，就不要說「你之前的決定」。講團隊內容時，用共享目錄裡真實存在的成員和專案舉例。
- **一次只問一個決定。** 匯入範圍、是否正式匯入、是否貢獻給團隊、協作約定各自單獨一輪，等他回答後再進入下一步。
- **四處決定都用選項工具問。** 選匯入範圍（3a）、確認正式匯入（3b）、貢獻給團隊（步驟 4）、協作約定（步驟 5）這四處，只要宿主有讓使用者點選答案的工具（見[附錄 A](#附錄-a各宿主說明)下的「選項工具」），就一定用它問，不要把選項寫成文字列表。步驟裡標著「**問題（選項工具）**」的地方就是呼叫點。工具裡只放一個問題和兩到三個選項，選項標籤要短，補充說明放進選項描述，推薦的放第一個、標「（推薦）」。工具自帶自由輸入，不要再加「其他」。只有工具列表裡沒有這類工具，或者呼叫報錯時，才用文字列出同樣的選項，不要重試。
- **要他看的內容放在他一定看得到的地方。** 問題文字要能單獨看懂：把做決定要用的要點（試執行找到了什麼、要貢獻哪些內容、約定寫入的檔案路徑）寫進問題裡，不要只寫「按上面的……」。有的宿主（例如 Codex 桌面版）在本輪結束後會把呼叫工具前後的過程訊息摺疊起來，只留下最後一條回覆和問題卡片。所以連線結果和價值介紹、讀回、團隊已有內容的介紹、約定原文這些要他讀的內容，寫在本輪最後一條回覆的正文裡，不要寫在呼叫工具之前的過程訊息裡；選項卡片的問題只放要他決定的事，不要把讀回整段塞進卡片。
- **每條訊息都以一個讓他往下走的動作結束**：選項卡片，或者他要做的操作（例如信任 hooks、重啟、發「已重啟」），不要以陳述句收尾。發出前對一遍這一步「對使用者說」的列表，缺了哪項補上。用 `request_user_input_async` 這類不等回答的工具時，先呼叫工具，再寫最後一條回覆。
- 不提本指南的步驟編號，不提當前宿主用不上的步驟，不逐條轉述本指南。

## 基本規則

- **不列印、不復述 API key。** 安裝器把 key 存進本機的 `~/.openviking/ovcli.conf`（更新時會先備份舊檔案），這是連線必需的；除此之外，key 不能出現在規則、專案檔案、續接訊息或永久命令批准裡。不要開啟、列印或搜尋 `ovcli.conf`。需要服務地址和身份時，執行 `ov health` 或呼叫 OpenViking 的 `health` 工具。
- **按預設方式接入。** 自動儲存和召回保持開啟，hooks 全部信任，各步驟的推薦項照指南給出，約定原文照原樣寫入。這樣他才能完整體驗到 OpenViking 的作用。
- **只做本指南描述的改動。** 安裝器會給本機檢測到的每個受支援的 Agent 都裝上外掛，這是預期行為。你自己不要改其他 Agent 的配置，也不要改使用者專案裡的檔案，除非使用者明確要求。
- **貢獻到團隊就是對團隊公開。** 寫進 `viking://resources/` 的內容，團隊成員都能看到。只貢獻他確認過的內容；貢獻前檢查裡面沒有金鑰、帳號和個人隱私。只寫他自己的子目錄 `viking://resources/<user_id>/`：其他成員的目錄許可權上往往也能寫，但不要改、不要刪。寫入被拒（`PERMISSION_DENIED`）時不要換位置寫，告訴他找團隊管理員。
- **用本指南給出的命令。** 不要去 GitHub 讀原始碼另找安裝或配置的方法；引數不確定時看命令的 `--help`。
- **按事實說話。** 讀回的內容、對團隊共享目錄的介紹，都必須來自 OpenViking 實際返回的結果。沒有真實內容時，不要編示例記憶或示例專案來演示效果。
- 命令失敗時，到[故障排查](https://docs.openviking.net/agents/zh/onboarding-troubleshooting.md)找對應現象，修好後重試一次。仍然失敗，就告訴使用者哪一步沒成、影響什麼、他可以怎麼處理。只有當前宿主的連線或認證失敗才阻塞後續步驟，其他宿主裝失敗不影響當前宿主；團隊共享目錄讀不到或寫不進，也不影響他自己空間的接入。

## 從哪一步開始

- **使用者給了安裝命令**：原樣執行它，再從步驟 1 開始。本機已經有 `ov` 命令或 `~/.openviking/ovcli.conf` 不算已安裝，外掛可能還沒裝上；安裝器可以重複執行，會先備份舊配置。不要改用宿主自己的外掛命令（例如 `codex plugin add`）另行安裝。命令裡還留著 `<API_KEY>` 這類佔位符時，先請他換成真實值，不要原樣執行。
- **安裝器是你在當前對話裡執行的**：從步驟 1 開始。
- **使用者說「已重啟」，而這段對話裡已經走過本指南前面的步驟**：使用者退出後恢復了原來的會話。直接跳到[重啟之後](#重啟之後)，前面的選擇都在對話裡，不要重問。
- **新會話裡，使用者發來一條「從……「重啟之後」繼續」的訊息**：跳到[重啟之後](#重啟之後)，以訊息裡寫的結果為準。
- **使用者只說了「已重啟」，但這段對話裡沒有前面的接入過程**（例如 `codex resume --last` 回到了別的會話，或者他開了新會話）：同樣跳到[重啟之後](#重啟之後)，在第 2 步先問清匯入、團隊貢獻和協作約定做到了哪一步，缺的逐個補上。
- **OpenViking 在這段對話之前就已安裝**（能看到 `<openviking-context>` 塊，或者有 `health` 等 OpenViking 工具；只有 `ov` 命令不算），使用者也沒給安裝命令：先用 `ov health` 或 `health` 工具查連線，記下返回的使用者名稱，告訴使用者連的是哪個服務、哪個使用者，問他沿用還是更換。
  - 沿用：做步驟 2 到 5，然後直接進入[重啟之後](#重啟之後)。不需要重啟。
  - 更換：請他在自己的終端裡執行工作臺給的安裝命令（或下面那條），再開一個新會話把工作臺的一鍵提示詞發給 Agent。舊配置會被備份，雲端資料不會被清空。
- **還沒有任何連線，使用者也沒給安裝命令**：請使用者提供服務地址和他自己的 API key（團隊成員在 OpenViking 工作臺的「接入 Agent」裡取，管理員在 OpenViking 控制台的使用者管理 → API Key 裡取），然後執行下面的命令，`<值>` 取[附錄 A](#附錄-a各宿主說明)的 `--harness` 列，再從步驟 1 開始。`cli` 一定要帶上：後面檢查連線、讀回內容和新增檔案都要用 `ov` 命令。

  ```bash
  curl -fsSL https://openviking.ai/install | bash -s -- --yes --lang zh --harness <值>,cli --url <服務地址> --api-key <使用者的 key>
  ```

- **使用者只想追加匯入歷史**：只做步驟 3，不重走安裝和協作約定。
- **使用者只想把某個專案貢獻給團隊**：只做步驟 4。

## 步驟 1：連線結果

**使用者要感受到什麼**：「我的 OpenViking 連上了；以後在這個 Agent 裡，我的上下文能延續，還能用上團隊其他成員的上下文。」（T1、V3）

**你來做**

閱讀安裝器的輸出，中文和英文兩種寫法都要認。

- 輸出最後有 `未完成` 列表（英文 `Not done`）時，按宿主判斷，不要因為前面有 `完成` 就說全部裝好了。當前宿主裝失敗、key 被拒或連不上服務，先按故障排查處理；只有其他宿主失敗時，在訊息裡簡單帶一句，繼續當前宿主。
- `完成`（英文 `Done`）一節按工具列出結果，每個工具有一行 `下一步：`（英文 `Next:`），寫著它怎麼重啟。確認當前宿主在列表裡；不在的話，見故障排查的「當前宿主不在 `完成` 裡」。
- 然後執行一次 `ov health`：確認連線，並**記下它返回的使用者名稱**。後面寫協作約定、新增檔案、在團隊目錄下建自己的子目錄都用這個使用者名稱，不用再查。安裝器輸出裡已經有 `服務檢查通過：<url>`（英文 `Server check passed`）時，這一步主要是為了拿到使用者名稱。
- 再按步驟 4 第 1 項看一眼團隊已有什麼（`ov ls viking://resources --include-abstract`、`ov ls viking://agent/skills --include-abstract`），記下結果，步驟 1 和步驟 4 都用它，步驟 4 不用再查。

**對使用者說**

不單獨發一條訊息。這是使用者第一次從你這裡聽說 OpenViking 能做什麼，放在步驟 2 那條訊息的開頭，三小段：

1. **連上了**，一句：已經連上他所在團隊的 OpenViking，外掛裝進了哪幾個 Agent（用產品名，例如 Codex、Claude Code）。裝進了不止一個時，順帶說出好處（V3）：以後在這些 Agent 裡都能接著同一份上下文工作。
2. **OpenViking 是什麼**，一句（定位）：它是 Agent 的外接上下文層，他的背景、決定和工作成果存在這裡，不隨會話結束消失，換會話、換 Agent 都能接著用。
3. **團隊裡怎麼協作**，兩三句（T1、T2、T4），用剛看到的真實內容講：每個人有自己的私有空間，記憶和對話只有自己能看到；團隊有一個共享目錄，現在已經有 <一兩個真實的目錄或專案>，同事的 Agent 遇到相關問題會直接查到、接著用；有共享技能時帶上數量和一個例子。目錄為空或讀不到時，說共享目錄還沒有內容，他可以做第一個貢獻者。最後一句預告接下來的安排：先把他過去的工作帶進來，再決定貢獻什麼給團隊，最後約好以後怎麼協作。

第 3 段參考說法（換成他的語言和真實內容）：「團隊版裡，你有自己的私有空間，記憶和對話只有你能看到；團隊還有一個共享目錄，現在已經有 branding 和 Gateway 方案這些資料，你的 Agent 遇到相關問題會直接用上；你也可以把自己的方案和進展放進去，讓同事接上。接下來我先把你之前的工作帶進來，再看要貢獻什麼，最後和你約好以後怎麼協作。」

不要說帳戶名、角色、服務地址和命令名。使用者有多個 OpenViking 帳號或問起時，再告訴他連的是哪個使用者。

## 步驟 2：以後會自動發生什麼

**使用者要感受到什麼**：「以後不用每次重新交代背景，聊過的東西會自己積累下來。」（V1）

**你來做**

- 查[附錄 A](#附錄-a各宿主說明)裡當前宿主的三件事：要不要信任 hook（以及能不能在重啟前先信任）、使用者在哪裡能看到 OpenViking 起作用、重啟後回原會話還是開新會話。
- 不用問使用者要不要開啟自動記憶，安裝本身就是他的請求。
- 使用者問起怎麼在某個專案裡關掉時，再告訴他：在該專案裡放一個 `.openviking/config.json`，內容為 `{"version": 1, "capture": {"enabled": false}, "recall": {"enabled": false}}`。只告訴他方法，不替他建立。

**對使用者說**

接在步驟 1 那三小段之後，用兩三行講：

1. V1：以後每次提問前，相關的背景（包括團隊共享的）會自動帶給 Agent；每輪對話也會自動存進他自己的空間，慢慢積累成背景。自動儲存的對話只有他能看到，不會進團隊共享目錄。用他當前的專案或請求舉一個例子。
2. 在哪裡能看到它起作用，用附錄 A 裡使用者能直接看到的樣子說，例如「回答下面會多一行 OV-Usage」。
3. 重啟後才生效時，說一句「重啟之後就開始生效，最後我會告訴你怎麼做」。需要信任 hook 的宿主，補一句「最後會請你確認一次 OpenViking 的 hooks」。具體操作留到步驟 6。

這條訊息末尾接上 3a 的價值一句，然後用選項工具發出 3a 的問題。這條訊息不講 hook 的事件名、儲存和提取的先後、怎麼關閉。

## 步驟 3：帶入已有工作

**使用者要感受到什麼**：「過去的討論能變成有據可查的背景。這次我已經親眼看到，它從裡面找回了我的工作。」（V2）

這一步最多三輪：選範圍 → 確認匯入 → 讀回結果。讀回是這一步的重點，匯入本身只是手段。

### 3a 選範圍

**對使用者說**：一句價值，最好說成他的專案：「把之前的討論帶進來，以後問 <專案> 上次做到哪、當時為什麼這麼定，就有依據」。

**問題（選項工具）**：帶入哪些已有工作？

- <當前專案名> 最近 14 天的討論（推薦）
- 指定一類工作或其他專案，描述寫「例如『和支付重構有關的討論』」
- 先不匯入，從現在開始積累

推薦的永遠是第一項，標籤裡寫出專案名和時間範圍；「先不匯入」不能標推薦。其他範圍（其他時間段、所有專案）由他在工具的自由輸入裡寫。

**你來做**：他選好之前，不要下載指令碼或試執行。匯入指令碼能直接讀 Claude Code 和 Codex 的歷史（`--harness claude` 或 `--harness codex`）。在其他宿主上：本機有 `~/.claude/projects` 或 `~/.codex/sessions` 時，可以把那邊的歷史作為一個選項一併提出；宿主自己的會話先按[其他宿主：把會話轉成 JSONL](https://docs.openviking.net/agents/zh/onboarding-other-hosts.md)轉換。

### 3b 試執行

**你來做**

選 1 或自定範圍：下載指令碼並試執行（不會上傳任何內容）。把 `<claude|codex>` 換成實際值；自定範圍時，`--cwd` 換成那個專案的目錄，「所有專案」用 `--all-projects` 代替 `--cwd`，時間改 `--since`（例如 `30d`、`2026-09-01`、`all`）。

```bash
curl -fsSL https://docs.openviking.net/dl/memory-plugin-shared/import-history.mjs -o "${TMPDIR:-/tmp}/ov-import-history.mjs" && node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 14d --max-sessions 20 --dry-run --json
```

選 2：先用 `--list` 列出範圍內的會話（每個帶 id、時間、訊息數、狀態，以及第一條和最後一條請求的摘要）。範圍按使用者的描述定，沒說就用當前專案、最近 30 天。按摘要挑出和他描述相符的會話，再用挑中的 id 試執行（多個 id 用逗號隔開；用 `--session` 時不受專案、時間和數量的限制）：

```bash
curl -fsSL https://docs.openviking.net/dl/memory-plugin-shared/import-history.mjs -o "${TMPDIR:-/tmp}/ov-import-history.mjs" && node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 30d --max-sessions 50 --list --json
node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --session <id>,<id> --dry-run --json
```

看試執行 JSON：`toImport.sessions` 是要新上傳的會話數；`sessions[].state` 為 `imported`（匯入過）或 `live`（外掛已經儲存過）的會話已經在 OpenViking 裡。因「仍在活動」而跳過的會話包括當前這段對話。

- **`toImport.sessions` 為 0，但有 `imported` 或 `live` 的會話**：這些內容已經在 OpenViking 裡，不用上傳，也不用問他確認。直接進入 3c 讀回。
- **範圍內沒有任何會話**：告訴他這個範圍裡沒找到，問他換個範圍還是先不匯入。
- **有要上傳的會話**：按下面的方式請他確認。

**對使用者說**（有要上傳的會話時）：三四行。

- 找到了什麼：用摘要說是哪些工作（選 2 時說你挑了哪幾個、沒挑上的大致是什麼），不報 id。
- 多大：幾個會話，大約多少字。
- 會傳什麼：只有他和 Agent 說的文字；工具呼叫和輸出、檔案原件不包括，已知格式的金鑰會被替換掉。

**問題（選項工具）**：照這個範圍匯入嗎？選項：匯入（推薦）／先不匯入。想調整範圍，他在自由輸入裡說。

### 3c 匯入並讀回

**你來做**

零新增時跳過匯入，直接讀回。使用者確認後，用**完全相同的範圍引數**，把 `--dry-run` 換成 `--yes --wait` 正式匯入（`--wait` 最多等兩分鐘的記憶提取）：

```bash
node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 14d --max-sessions 20 --yes --wait --json
```

看 JSON 裡每個會話的 `extraction`，不要只看退出碼。

然後**讀回**。只要有會話進了 OpenViking（這次匯入的、之前就匯入過的、外掛已經儲存的），都要讀回。`--wait` 返回時，`extraction` 為 `completed` 的會話已經提取成記憶，所以讀回讀的是記憶，不是會話本身。外掛要重啟後才在這段對話里加載，所以這裡用 `ov` 命令：

1. 在他的整個使用者目錄下檢索記憶，查詢詞用他描述的工作或專案名。匯入提取出的記憶分在兩處：`viking://user/<user_id>/memories/`（跨專案的實體、事件、偏好）和 `viking://user/<user_id>/peers/<專案>/memories/`（這個專案的實體、事件、偏好；`<專案>` 是匯入 JSON 裡的 `projectPeer`）。以使用者目錄為範圍檢索一次，兩處都會覆蓋到：

   ```bash
   ov find "<他描述的工作或專案名>" -u viking://user/<user_id> --context-type memory -n 10
   ```

   只想看這次匯入新提取的記憶時，加上 `--after`，取匯入開始前的時間，例如 `--after 30m`。

2. 從結果裡挑兩三條最相關的，重點看上面兩處 `memories/` 下的實體（`entities/`）和事件（`events/`）記憶，用 `ov read` 讀全文。實體記憶講這項工作或這個物件是什麼、現在什麼狀態；事件記憶有摘要，也帶著當時的對話原文：

   ```bash
   ov read <記憶的 URI>
   ```

3. 只有兩種情況讀匯入的原對話：他想看當時的原話，或者沒有提取出記憶（`extraction` 不是 `completed`，或者第 1 步什麼都沒查到）。直接讀歸檔裡的原始訊息：會話 id 用匯入 JSON 裡的 `id`，匯入只提交一次，歸檔就是 `archive_001`。不要用 `ov session get-session-archive`，較舊的服務端只返回記憶整理完成的歸檔，正好在這兩種情況下可能找不到。外掛儲存的 `live` 會話不用讀原對話，以第 1 步的結果為準：

   ```bash
   ov read viking://user/<user_id>/sessions/<會話 id>/history/archive_001/messages.jsonl
   ```

4. 從讀到的內容裡整理四件事：這項工作要做成什麼、上次做到哪、定過的一個判斷和理由、還沒解決的事。找不到的項就不寫，不要補。另外記下一個**缺口**：討論裡提到、但原文不在 OpenViking 裡的成品，例如方案文件、指令碼、報告。步驟 4 和步驟 5 會用到它。也記下匯入的是哪個專案、它在本機的目錄（`--cwd` 的值）。

| 匯入結果 | 第一句怎麼說 | 讀回 |
|---|---|---|
| 有寫入，`extraction` 為 `completed` | 匯入了哪幾項工作，記憶已經整理好 | 讀記憶：`ov find`，再 `ov read` 一兩條 |
| 有寫入，提取還在進行（`pending`、`running`）或沒有結果 | 討論已經存進去了，記憶還在後臺整理，幾分鐘後就能被自動取回 | 讀原對話（`messages.jsonl`），並說明「這是從原對話裡讀到的」 |
| `failed` | 討論已儲存，但記憶整理失敗了，之後可以重試 | 讀原對話 |
| 零新增：都已匯入過或外掛已儲存 | 這些討論之前就已經在他的 OpenViking 裡，這次不用重複上傳 | 讀記憶（不加 `--after`） |
| 部分失敗 | 哪些成功、哪些失敗，失敗的之後可以重試，不要全部重傳 | 讀成功的部分 |
| 沒有匹配，或使用者選了不匯入 | 以後從他的真實工作開始積累 | 不讀，直接進入步驟 4 |

使用者問起指令碼做了什麼時：它只讀本機的會話檔案（Claude Code 在 `~/.claude/projects/`，Codex 在 `~/.codex/sessions/`），只保留使用者和助手的文字，清洗已知格式的金鑰，跳過近期仍在活動的會話，並沿用外掛的專案歸屬，所以匯入的歷史和以後的對話在同一個專案下。試執行和 `--list` 只從服務端讀，用來找出已經匯入過的會話。

**對使用者說**

1. 第一句：上表「第一句怎麼說」。不報訊息數、字數、`extraction` 這類狀態名。
2. 讀回，兩到四條，用他的原話和名詞：在做什麼、上次做到哪、定過什麼（連同理由）、還差什麼。有多項工作時每項一行，不展開。讀回寫在這條訊息的正文裡；下一步的選項卡片只用一句話提到它。
3. 一句價值（V2 + V3）：「以後在任何接入的 Agent 裡問『<工作> 做到哪了』，都能從這裡接上。」

這條訊息不問要不要開始做這項工作，也不列狀態清單。接著在同一條訊息裡進入步驟 4：團隊已經共享了什麼。

### 檔案

使用者點名了值得儲存的檔案或資料夾（例如設計文件、需求說明）時，逐個新增到他個人資源裡這個專案的目錄下，作為其中的一項（不要把專案目錄本身作為匯入目標）。`<user_id>` 用步驟 1 記下的使用者名稱，`<專案名>` 用倉庫名或他對這個專案的叫法：

```bash
ov add-resource ./docs/design.md --parent-auto-create viking://user/<user_id>/resources/<專案名> --wait
```

只新增他點名的內容，不要自己掃描目錄或主動上傳。新增後告訴他存好了、以後怎麼找（「說『按 <檔案> 繼續』就行」），不報 URI。

## 步驟 4：貢獻團隊資產

**使用者要感受到什麼**：「團隊已經在共享目錄裡留下了這些上下文，我的 Agent 能直接用；我也可以先貢獻一些，讓同事接上我的工作。」（T2、T3、T4）

**你來做**

1. **看團隊已有什麼。** 在步驟 1 做，這裡沿用結果，只在需要時補查和他工作相關的目錄。列出共享目錄第一層和共享技能，帶上摘要（L0）。第一層通常按成員（目錄名就是他的使用者名稱）或按專案分；和他的工作相關、或摘要看不出內容的目錄，再往下列一層，需要時讀概覽（L1）。最多看 10 個目錄，標著 `permission denied` 的跳過、不提：

   ```bash
   ov ls viking://resources --include-abstract
   ov ls viking://agent/skills --include-abstract
   ov ls viking://resources/<目錄> --include-abstract
   ov overview viking://resources/<目錄>
   ```

   記下誰或哪個專案貢獻了什麼，以及共享技能的數量、名字和各自做什麼。共享目錄是空的，記下「還沒有人貢獻」；整個讀不到（報錯或許可權不足），記下原因，跳過貢獻，直接進入步驟 5。

2. **準備貢獻候選**：一個專案的重點方案、產出和進展。專案用步驟 3 匯入的那個（`<專案目錄>` 是 3c 記下的 `--cwd` 值）；沒有匯入時用當前目錄（`$PWD`）所在的專案。

   - 文件：找匯入時間範圍內（沒有匯入時用最近 14 天）改過的方案、調研、需求、設計、報告，只列出、不上傳，挑最多 5 份，步驟 3 的缺口和會話裡提到過的優先。README、CHANGELOG、程式碼說明、模板，以及含金鑰、帳號、個人隱私的檔案不選：

     ```bash
     find "<專案目錄>" -type f \( -name '*.md' -o -name '*.pdf' -o -name '*.docx' -o -name '*.pptx' -o -name '*.xlsx' \) -mtime -14 -not -path '*/node_modules/*' -not -path '*/.git/*' -not -path '*/dist/*' -not -path '*/build/*' | head -50
     ```

   - 步驟 3 已經存進他個人空間的檔案（見上面「檔案」）：也列為候選，不要再從本地上傳一份。
   - 進展摘要：只在 3c 讀回了內容時準備，就是讀回的四件事。沒有讀回時不準備，也不要從本地文件或匯入摘要另外拼一份。

   當前目錄不是一個專案（例如主目錄），或者既沒有合適的文件、也沒有讀回時，沒有候選。

3. **他同意後貢獻**，放進 `viking://resources/<user_id>/<專案名>/`（`<user_id>` 是步驟 1 記下的使用者名稱，`<專案名>` 用倉庫名或他對這個專案的叫法）：

   ```bash
   # 文件，逐個新增（目錄不存在時自動建）
   ov add-resource <文件路徑> --parent-auto-create viking://resources/<user_id>/<專案名> --wait
   # 步驟 3 存進個人空間的檔案：移過來，不留兩份。mv 不會建目錄，目標目錄還不存在時先 mkdir；條目名取自 ov ls viking://user/<user_id>/resources/<專案名>
   ov mkdir viking://resources/<user_id>/<專案名>
   ov mv viking://user/<user_id>/resources/<專案名>/<條目名> viking://resources/<user_id>/<專案名>/<條目名>
   # 進展摘要：先在臨時目錄寫好 Markdown（首行「<專案名> 進展，更新於 <日期>」，內容是那四件事），寫入後刪掉臨時檔案
   ov write viking://resources/<user_id>/<專案名>/notes/progress.md --from-file "${TMPDIR:-/tmp}/ov-progress.md" --wait
   ```

   完成後 `ov ls viking://resources/<user_id>/<專案名>` 確認都在。返回 `PERMISSION_DENIED` 時停止貢獻，不要換位置寫；內容還在他本地和他自己的空間裡，以後有了許可權可以再貢獻。

**對使用者說**

接在步驟 3 的讀回之後：

1. **團隊已經有什麼**，一兩句，接著步驟 1 講過的內容，點出和他剛匯入的工作相關的那部分及用處（T2、T3），例如「團隊目錄裡的 <目錄> 和你這項工作相關，以後問『<專案> 現在定了什麼』，你的 Agent 會直接用上」。沒有相關的，就說團隊目錄裡還沒有這項工作的內容。
   - 共享目錄是空的：「團隊共享目錄還是空的，你可以做第一個貢獻者。」
   - 讀不到：「團隊共享目錄你現在還讀不到，可能需要管理員開許可權；這不影響你自己的空間。」然後進入步驟 5，不問貢獻。
2. **貢獻的意義**（T4），一句：把方案和進展放進團隊目錄下你自己的資料夾，同事的 Agent 就能接上你的工作，不用你再講一遍。
3. **誰能看到**，一句：團隊成員都能看到；你的記憶、會話和個人空間裡的資料不會共享。

**問題（選項工具）**：問題寫出要貢獻什麼、放在哪，例如「要不要把 Gateway 專案的 2 份方案文件和一份進展摘要貢獻給團隊？會放在團隊目錄下你的資料夾裡，團隊成員都能看到。」選項：

- 貢獻 <一句話說內容，例如「Gateway 專案的方案、調研文件和進展」>（推薦）
- 暫不貢獻，再想想

在問題或描述裡提一句：想換內容或換存放位置，在自由輸入裡直接說；他改了以後，按新的範圍再問一次。

沒有貢獻候選時也要問，讓他知道可以貢獻、由他決定內容。問題例如「要不要現在把某個專案的方案或進展貢獻給團隊？會放在團隊目錄下你的資料夾裡，團隊成員都能看到。」選項：

- 我來指定內容，描述寫「告訴我要貢獻的檔案或專案」
- 暫不貢獻

他指定後，按上面的方式準備候選、說清要貢獻什麼，再問一次。暫不貢獻時說一句「以後有想給團隊看的方案或進展，說『把 <專案> 的進展貢獻給團隊』就行；接下來的協作約定也會帶上這件事。」然後進入步驟 5。

貢獻完成後一句話說結果：貢獻了哪幾項、在團隊目錄下他的哪個資料夾，同事的 Agent 現在就能檢索到。暫不貢獻時說「以後想貢獻，說『把 <專案> 的進展貢獻給團隊』就行」。然後進入步驟 5。

## 步驟 5：約定以後怎麼協作

**使用者要感受到什麼**：「接下來我和 <Agent> 約好怎麼用 OpenViking 留存和找回工作上下文、哪些放進團隊目錄，之後它會一直按這個約定做；約定由我定，也可以按我的角色來定。」（V4、T4）

**你來做**

1. 找當前宿主實際讀取的使用者級規則檔案（[附錄 A](#附錄-a各宿主說明)「使用者級規則檔案」一列是常見位置，以宿主實際讀取的為準），看裡面有沒有 `<!-- openviking:start -->` 標記塊。

   - 沒有：準備下面的原文。
2. 準備約定原文。預設用下面這段；使用者調整了，或按角色加了內容，就按他的選擇改。把 `<user_id>` 直接換成步驟 1 記下的使用者名稱，寫入前不用再查；`<專案名>` 保持原樣，它在每個專案裡各自確定。

   - 檔案裡已有和這段約定衝突的要求（例如每輪都必須檢索，或者不許把資料存到外部），先告訴他衝突在哪，按他的決定改。

   - 不要寫進專案檔案。

**對使用者說**

這一輪最後一條回覆的正文**只有下面三段，按順序，缺一不可**，然後呼叫選項工具。不要另寫一份摘要來代替原文，也不要只貼原文不講為什麼：原文本身就是給他看的說明。

1. **為什麼這樣約定**，一兩句（V4、T4）：接下來和 <當前 Agent 的名字> 約好以後怎麼用 OpenViking；自動記憶只留下對話要點，方案、決定和進展要主動存一份，以後才能原樣拿回來，預設放進團隊目錄，同事的 Agent 才能接上他的工作。步驟 3 記下了缺口時，用它開頭：「會話裡有討論，但 <成品> 的原文不在裡面。」
2. **原文**：「下面這段會寫進 <規則檔案的完整路徑>，對你所有專案生效，隨時可以改：」，再用程式碼塊給出原文。**原樣給出，只把 `<user_id>` 換成他的使用者名稱**，不要改寫、刪減或改動預設存放位置；他要求改了以後，才給改後的版本。
3. **問題（選項工具）**：卡片裡只寫要他決定的事和檔案路徑，不再重複原文要點，例如「按上面這段約定寫入 <規則檔案路徑> 嗎？」選項：
   - 按這個方式約定（推薦）

   - 只用自動記憶

   在描述裡提一句：想改原文的哪裡，可以在自由輸入裡直接說。

接下來：

- **按這個方式約定**：寫入。
- **按我的角色調整**：問他的角色（用文字問一句即可），給出調整後的原文，一句話說新增了哪條，再用選項工具問：按這個寫入（推薦）／再調整／只用自動記憶。

## 步驟 6：重啟

**使用者要感受到什麼**：「再做一步就能用上了，回來後直接接著我的工作。」

**你來做**

- 當前宿主已經生效、本次也沒有新裝外掛時，跳過這一步，直接進入[重啟之後](#重啟之後)。
- 查[附錄 A](#附錄-a各宿主說明)當前宿主的「重啟或信任」和「重啟後」兩列，以及安裝器輸出裡其他工具的 `下一步：`（英文 `Next:`）。
- 準備續接訊息。網址用你實際開啟成功的那個；本指南是本地檔案時，用它的絕對路徑。尖括號換成實際結果，其他照寫，不要加「先驗證檢索」之類的額外任務：

```text
已重啟。從 https://docs.openviking.net/agents/zh/onboarding-team.md 的「重啟之後」繼續 OpenViking 團隊版接入。歷史匯入：<例如「匯入了 2 個會話」「已在 OpenViking 裡」「已跳過」>；團隊貢獻：<例如「貢獻了 Gateway 專案的方案和進展」「暫不貢獻」「團隊目錄讀不到」>；協作約定：<已寫入 / 未寫>；接下來想做：<他說過的目標，沒說就寫「未說」>。
```

**對使用者說**

1. 現狀，用肯定的說法：連上了團隊的 OpenViking、帶進了哪項工作、給團隊貢獻了什麼。協作約定寫了的話，一句話說寫進了哪個檔案，以後想看或想改，開啟它或直接讓你改；沒寫就說沒寫。
2. 一句預告：「回來後可以接著 <工作> 做，也可以先看看團隊共享了什麼，你來選。」沒帶入工作時說：「回來後直接告訴我你要做的事，或者先看看團隊共享了什麼。」
3. **需要信任 hook 的宿主（Codex、TraeCode CLI 2.0），請他在退出前先信任**：Codex 桌面版點輸入框下方的 hooks 圖示，Codex CLI 和 TraeCode CLI 在會話裡輸入 `/hooks`，信任 OpenViking 的**全部** hooks。說一句好處：信任之後每次提問才會自動帶上背景、對話才會自動積累，重啟後也不會停在審閱提示上。重啟後如果還是出現「Hooks need review」，照舊選 **Trust all and continue**。
4. 當前宿主怎麼重啟。
5. 安裝器還裝進了其他 Agent 時，加一行點出名字：各自重啟後生效，具體看安裝器輸出裡的「下一步」。
6. 回來之後做什麼：
   - 「重啟後」一列寫著回到原會話的宿主：告訴他用表裡的命令回到**這段對話**，然後發一句「已重啟」。續接訊息也給他，作為備用：回到的不是這段對話時，在新會話裡發它。
   - 寫著開新會話的宿主：告訴他開一個新會話，不要恢復這段對話，也不要在這裡重新載入外掛，並給他續接訊息。

預告放在前面，訊息最後是要他做的操作（信任 hooks → 重啟 → 回來發什麼）。說完就停下，等使用者操作。

## 重啟之後

**使用者要感受到什麼**：「它真的接上了：我沒交代背景，它就知道我在做什麼，還能用上團隊的上下文。」（V1、V2、T2）

**你來做**

1. **確認外掛在執行。** 當前對話裡有 `<openviking-context>` 塊，或者 OpenViking 工具可用。呼叫 `health` 工具（名字可能帶字首，例如 `mcp__openviking__health`、`openviking_health`）。都沒有時，見故障排查的「重啟後沒有召回」。有注入塊才說明自動召回在執行；沒有相關記憶，可能只是庫裡還沒有相關內容。
2. **補上缺的選擇。** 從這段對話或續接訊息裡確認匯入、團隊貢獻和協作約定是否已經做完。缺了就補做那一步，做過的不要重問。
3. **取回背景。** 先用注入的上下文；不夠再用 `search`（`mode="context"`）查，必要時 `read` 原文。只查團隊內容時用 `find` 並設 `target_uri="viking://resources"`（`mode="context"` 不接受 `target_uri`）；列團隊目錄用 `list`；找團隊技能用 `find` 並設 `context_type="skill"`。記憶還在整理時，可以用 `read` 讀匯入的原對話（`viking://user/<user_id>/sessions/<會話 id>/history/archive_001/messages.jsonl`），但要說明這是讀的原記錄。

**對使用者說**

按他想要的結果選一種；他沒說（續接訊息裡是「未說」）時，把前兩種作為選項給他：

| 他想要的 | 訊息內容 |
|---|---|
| 接著過去的工作做 | 這項工作要做成什麼、上次做到哪、定過哪些判斷、還有什麼沒解決；再給兩三個具體的推進方向。點出其中一條依據是從 OpenViking 取回的、它怎麼影響了你的建議（V1）；團隊目錄裡有相關內容時，也點出一條（T2）。有多項工作時先讓他挑一項。 |
| 瞭解團隊共享的上下文 | 按成員或專案列出團隊目錄裡和他相關的兩三個方向，請他挑一個；挑好後讀那個目錄的概覽和一兩份資料，講清楚這裡有什麼、已經定了什麼、對他手頭的工作有什麼用（T2、T3）。團隊共享技能裡有和他的工作相關的，也點出來，說清能幫他做什麼。 |
| 儲存或複用一份資料 | 按他點名的檔案新增後讀回，或者讀已有的資料回答他一個真實的問題；告訴他以後怎麼找回，以及存在團隊目錄還是個人空間。 |
| 從現在開始，或者暫時不體驗 | 一句以後會怎麼積累，請他直接開始一件真實的工作，或者稍後再用。 |

給出總結和方向後，等他選，不要直接動手改程式碼或推進任務。

**收尾**，最多三行，接在他選完方向之後或這條訊息末尾：

- 已經在起作用的，以及還在後臺進行的（例如記憶整理）。還沒確認的狀態在這裡統一說一次。
- 在這個宿主上哪裡能看到 OpenViking 的作用（附錄 A 的「在哪裡能看到」）。
- 以後可以說的話，挑一兩條和他相關的：「看看團隊最近共享了什麼」「把 <專案> 的進展貢獻給團隊」「把 <技能> 共享給團隊」「把 <專案> 的會話匯入 OpenViking」「儲存這份文件，之後按它繼續」「換一個 OpenViking 帳號」（按[從哪一步開始](#從哪一步開始)裡「更換」的做法處理）。裝進了其他 Agent 時提一句：在那邊接著這項工作，背景還在（V3）。

  - Codex：有兩個，工具列表裡有哪個用哪個，優先 `request_user_input_async`。
    - `request_user_input_async`：gpt-6 系列等模型在 Default 模式下也有（例如 Codex 桌面版 0.164）。它把問題作為一張選項卡片發出、不等回答，使用者的選擇會作為下一條訊息回來。Codex 桌面版會在本輪結束後摺疊過程訊息，所以呼叫它之後，把要他讀的內容寫進本輪最後一條回覆。
    - `request_user_input`：只在 Plan 模式下可用（使用者開了 `default_mode_request_user_input` 時 Default 模式也能用），否則呼叫會返回 `request_user_input is unavailable in Default mode`。
    - Codex 的 Default 模式指令也要求不要把多選題寫成文字訊息。兩個都不可用時才用文字問。
  - 這些工具都會自動加一個「Other」讓使用者自己輸入，不要在選項裡再放「其他」。其他宿主有同類工具就用，沒有就用文字。
- **無文件說明。** 在這些宿主上，使用者可以直接問你收到了哪些 OpenViking 上下文，也可以執行故障排查裡的診斷。

各宿主的詳細說明：https://docs.openviking.net/zh/agent-integrations/01-overview
